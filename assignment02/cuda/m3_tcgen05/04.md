# 3.4 cta_group::1 vs cta_group::2 实验

GPU: NVIDIA B300 SXM6 AC(CC 10.3),driver 580.126.09。程序未修改。

## (a) 预测 + 运行验证

| 量 | ::1 每 CTA | ::2 每 CTA | 比值 | 预测 |
|---|---|---|---|---|
| B smem(`sB`) | 64·64·2 = 8192 B | 32·64·2 = 4096 B | 0.5 | ✓ 命中 |
| A smem(`sA`) | 128·64·2 = 16384 B | 16384 B | 1.0 | 不变 |
| smem/block(打印值) | 24588 B | 20492 B | 0.833 | — |
| TMEM(`tcgen05.alloc` 列数) | 64 | 64 | 1.0 | 每 CTA 存 128 行,两版一样 |

运行输出:

```
smem/block: cta_group::1 = 24588 B, cta_group::2 = 20492 B
::1  PASS(bad=0)  20.50 us      # 无 profiler,第一次跑
::2  PASS(bad=0)  22.43 us
```

要点:B tile 减半,但 smem/block 只降 4096 / 24588 ≈ 16.7%,因为 `sA`(128 行,16 KB)
是大头且两版完全相同。TMEM 不省——`::2` 的逻辑 M=256 结果按 128 行分落到两个 CTA
各自的 TMEM,和 `::1` 每 CTA 128 行一致。

### 分析

**1. Staging store:B 减半 ≠ 总流量减半。** store wavefront 778 → 650,只降 16.5%,和
smem/block 的 −16.7% 几乎一致。原因看两个 staging 循环:

- A 循环 `i < 128*K`(8192 elem / 128 线程 = 64 iter/线程)—— 两版完全相同,是 store 的主体。
- B 循环 `i < BROWS*K` —— `::1` 是 64·64,`::2` 是 32·64,迭代数减半。

只有 B 那部分(约 128 个 wavefront)被砍掉一半,A 那 ~650 个原封不动。所以省下的
smem 换来的 staging store 流量下降和容量下降同比例,都是被 A 主导的 ~1/6。

**2. Shared load 计数器看不到 Tensor Core 取 operand。** `_op_ld` 只有 26/29,这不是
MMA 读 A/B 的量。`tcgen05.mma` 通过 descriptor 走 async/tensor 代理直接从 smem 取
operand,不经过 LSU 的 `shared_ld` 路径,所以 LSU wavefront 计数器抓不到它。这 26~29
次是 `s_taddr[0]`、mbar 相关的 generic load;`::2` 多 3 次是 cluster 协作(读对端
taddr / 额外 barrier)。**要看 TC 侧的 shared wavefront 得从 `.ncu-rep` 的
Memory Workload Analysis 图里的 shared / async 行,或 `sm__pipe_tensor*` 系列取**,
不能用这里打印的两个 `_op_ld`。

**3. `hmma` tensor metric = n/a。** sm_100 上 `tcgen05.mma` 不计入 `hmma` 流水,是
tcgen05 / UMMA 路径。报告要引 tensor 利用率的话,换 `sm__pipe_tensor_cycles_active`
之类,从 `.ncu-rep` 里取。

**4. 单 tile 下 `::2` 不快。** active cycle 略少(355 vs 374),但 wall time 基本持平甚至
更慢。`cluster.sync()` ×2 + multicast commit + 跨 CTA mbarrier 的协作开销吃掉了省下的
那点 B staging。`::2` 的价值不在这个规模体现 —— 见 (c)。
