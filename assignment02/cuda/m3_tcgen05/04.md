# 3.4 cta_group::1 vs cta_group::2 实验

GPU: NVIDIA B300 SXM6 AC(CC 10.3),driver 580.126.09。程序未修改。

## (a) 预测 + 运行验证

| 量 | ::1 每 CTA | ::2 每 CTA | 比值 | 预测 |
|---|---|---|---|---|
| B smem(`sB`) | 64·64·2 = 8192 B | 32·64·2 = 4096 B | 0.5 | ✓ 命中 |
| A smem(`sA`) | 128·64·2 = 16384 B | 16384 B | 1.0 | 不变 |
| smem/block(打印值) | 24588 B | 20492 B | 0.833 | — |
| TMEM(`tcgen05.alloc` 列数) | 64 | 64 | 1.0 | 每 CTA 存 128 行,两版一样 |

运行输出:

```
smem/block: cta_group::1 = 24588 B, cta_group::2 = 20492 B
::1  PASS(bad=0)  20.50 us      # 无 profiler,第一次跑
::2  PASS(bad=0)  22.43 us
```

要点:B tile 减半,但 smem/block 只降 4096 / 24588 ≈ 16.7%,因为 `sA`(128 行,16 KB)
是大头且两版完全相同。TMEM 不省——`::2` 的逻辑 M=256 结果按 128 行分落到两个 CTA
各自的 TMEM,和 `::1` 每 CTA 128 行一致。

### 分析

**1. Staging store:B 减半 ≠ 总流量减半。** store wavefront 778 → 650,只降 16.5%,和
smem/block 的 −16.7% 几乎一致。原因看两个 staging 循环:

- A 循环 `i < 128*K`(8192 elem / 128 线程 = 64 iter/线程)—— 两版完全相同,是 store 的主体。
- B 循环 `i < BROWS*K` —— `::1` 是 64·64,`::2` 是 32·64,迭代数减半。

只有 B 那部分(约 128 个 wavefront)被砍掉一半,A 那 ~650 个原封不动。所以省下的
smem 换来的 staging store 流量下降和容量下降同比例,都是被 A 主导的 ~1/6。

**2. Shared load 计数器看不到 Tensor Core 取 operand。** `_op_ld` 只有 26/29,这不是
MMA 读 A/B 的量。`tcgen05.mma` 通过 descriptor 走 async/tensor 代理直接从 smem 取
operand,不经过 LSU 的 `shared_ld` 路径,所以 LSU wavefront 计数器抓不到它。这 26~29
次是 `s_taddr[0]`、mbar 相关的 generic load;`::2` 多 3 次是 cluster 协作(读对端
taddr / 额外 barrier)。**要看 TC 侧的 shared wavefront 得从 `.ncu-rep` 的
Memory Workload Analysis 图里的 shared / async 行,或 `sm__pipe_tensor*` 系列取**,
不能用这里打印的两个 `_op_ld`。

**3. `hmma` tensor metric = n/a。** sm_100 上 `tcgen05.mma` 不计入 `hmma` 流水,是
tcgen05 / UMMA 路径。报告要引 tensor 利用率的话,换 `sm__pipe_tensor_cycles_active`
之类,从 `.ncu-rep` 里取。

**4. 单 tile 下 `::2` 不快。** active cycle 略少(355 vs 374),但 wall time 基本持平甚至
更慢。`cluster.sync()` ×2 + multicast commit + 跨 CTA mbarrier 的协作开销吃掉了省下的
那点 B staging。`::2` 的价值不在这个规模体现 —— 见 (c)。

## (c) 省下的 smem 在 M4 pipeline 里换什么

`03_pipeline.cu` 的 tile 形状(`BM=128, BN=64, BK=64`)和这里的 `M,N,K` 完全一致,
可以直接对账:

- 一个 stage 的 B buffer = `BN*BK*2 = 64*64*2 = 8192 B`,和本题的 `sB`(`::1`)
  完全对应;一个 stage 的 A buffer = `BM*BK*2 = 16384 B`;一个 stage 总量
  `= 24576 B`(+对齐余量,`03_pipeline.cu` 注释里 `STAGES=3` 说的 "72KB" 就是
  `3*24576=73728 B` 取整)。
- `cta_group::2` 只砍 B(N 方向切半),把每 CTA 每 stage 的 B buffer 从 8192 B
  降到 4096 B,A 不变。换到 pipeline 语境:**省下的 4096 B/CTA 不是省出一整个
  stage,只是一个 stage 里 B 那部分的一半**,占单 stage 总量的
  `4096/24576 ≈ 16.7%`——和 (a)(b) 里算出的 smem/block 降幅、staging store
  降幅是同一个比例,不是巧合,`04_cta_pair.cu` 本来就是把 M4 的 tile 形状原样
  搬出来做的最小实验。

- **够不够单独换一级 stage?** 不够。在 `STAGES=S` 下,`::1` 布局总量
  `S*24576 B`,`::2` 布局总量 `S*20480 B`,差值 `S*4096 B`。以默认
  `S=3` 为例:`::1` 用 73728 B,`::2` 同样 3 级只要 61440 B,省下 12288 B
  ——不够再塞一级(不管是 `::1` 口径的 24576 B 还是 `::2` 口径的
  20480 B,12288 B 都不够付)。所以 `::2` 在这里换不来"白送一级 stage"。

- **真正能换的是两件事:**
  1. **同样 `STAGES` 下降 smem 占用 → 提高每 SM 常驻 block 数。** M4 4.3 的
     笔记里已经记录过"共享内存用量把每 SM 能同时驻留的 block 数摁住"这个
     现象(`report.md` 4.3 节 `Block Limit Shared Mem`);`::2` 把每 CTA 的
     smem 需求往下压一截,在同一张卡上能多塞进几个 block 并发驻留,用更多
     block 级并发去隐藏 TMA 延迟,而不是单个 kernel 实例内部的直接加速——这
     和 (b) 的结论(单 tile 规模下 `::2` 的 cluster 同步开销吃掉了它省下的
     staging)并不矛盾:`::2` 的价值要摊到更大的并发规模上才能兑现。
  2. **让 `STAGES` 本身能往上探一级而不越界。** 想从 `STAGES=3` 升到
     `STAGES=4` 时,`::1` 布局要多付 `24576 B`(总量 98304 B),`::2` 布局只
     要多付 `20480 B`(总量 81920 B)——同样目标 stage 数下,`::2` 让总 smem
     账单更接近可行区间,给"再深一级流水"腾出余量。

## (d) cta_group::2 依赖的硬件概念

**层 1:sm90 引入的 thread block cluster / 分布式共享内存(DSMEM)。**
一组 block 可以在 launch 时显式声明成一个 cluster(本题里就是
`cudaLaunchAttributeClusterDimension` + `cfg.attrs`),硬件保证 cluster
内的 CTA 被调度到同一个 GPC 内,并通过片上的 SM-to-SM 网络(不经过 L2/显存)
直接访问彼此的 shared memory,这就是 DSMEM。本题里 `cg::this_cluster().sync()`
(等两个 CTA 的 smem 都就绪 / 都读完 TMEM 才能 dealloc)、`tcgen05.commit`
末尾的 `multicast::cluster`(一次 commit 同时唤醒两个 CTA 的 mbarrier)都是
建在这层机制上的——没有 cluster/DSMEM,两个 CTA 之间既不能低延迟同步,也没有
"跨 CTA 唤醒 mbarrier" 这回事。

**层 2:tcgen05 与 cta_group::2 是数据中心 Blackwell(sm_100a)专属的更上层
扩展,不是 cluster 本身。** cluster/DSMEM 是 sm90+ 的通用编程模型,Hopper、
消费级 Blackwell(5090,sm_120)、数据中心 Blackwell(B100/B200/B300,
sm_100a)都支持;但 `tcgen05.*` 这一整条 TMEM 指令族(包括 `cta_group::1`)
只在 sm_100a 上暴露,5090 上根本没有 `tcgen05`,更谈不上 `cta_group::2`
——这也是为什么本模块的 `make run/m3_tcgen05/*` 固定 `ARCH=100f`,5090 若要
做同类 GEMM 只能走 4.4 里提到的 `mma.sync` 版本。`cta_group::2` 在这之上
再加一层:让 cluster 里的两个 CTA 各自出一半操作数、把结果按 M=256 拼成
一条 tensor core 指令,这要求 TMEM 本身也能被两个 CTA 按 pair 协作地
`alloc`/`dealloc`(本题 (a) 里"两个 CTA 的同号 warp 都必须发射"就是这层
协作的直接体现)。

**结合 0.2 表的数字说明为什么这类特性只出现在数据中心卡上:**

1. **算力涨得比带宽快,逼着你去抢内存墙。** B300 的 bf16 峰值(`tcgen05`
   上限)≈2240 TFLOPS,是 5090(≈419.5 TFLOPS)的 5 倍以上,机器平衡点也从
   5090 的 ≈234 FLOP/byte 推到 B300 的 ≈292 FLOP/byte。`cta_group::2` 让两个
   CTA 共享同一份 B 操作数(每个 CTA 只需取一半 N),本质是拿片上互联换
   DRAM/L2 带宽——平衡点越紧张,这笔交易的收益越大,数据中心卡显然更需要。
2. **SM 数量与互联拓扑是数据中心 die 才给得起的预算。** B300 148 个 SM 配的
   是为多 SM/多 GPU 协同设计的高带宽片内网络(cluster 的 SM-to-SM fabric)
   和卡间 NVLink;5090 是消费级 die,面向单卡桌面场景,面积/功耗预算里没有
   "让两个 SM 联合发一条 MMA、共享 TMEM" 这种跨 SM 协同通路的位置——这也是
   为什么 `tcgen05` 整条指令族(不只是 `cta_group::2`)只出现在 sm_100a。
3. **带宽差距没有算力差距大,缺口必须靠片上复用去补。** B300 HBM3e 实测带宽
   ≈7672 GB/s,是 5090 GDDR7(≈1792 GB/s)的 4 倍多,但算力差距(≈5×以上)
   比带宽差距更大——数据中心卡的"计算/带宽缺口"更严重,更需要靠
   cluster/DSMEM 这类片上数据复用机制去填,而不是单纯堆显存带宽。这和 0.2
   的结论("单条 mma 计算强度低是硬件形状决定的,能改的是数据供给路径")是
   同一条逻辑在 M3 层面的体现:`cta_group::2` 就是把"数据供给路径"从单 CTA
   内部(smem/TMEM)进一步扩展到跨 CTA(DSMEM)。
