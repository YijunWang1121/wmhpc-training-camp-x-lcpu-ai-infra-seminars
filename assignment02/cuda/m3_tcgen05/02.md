# 3.2 fence.proxy.async 实验

GPU: NVIDIA B300 SXM6 AC,driver 580.126.09。

## 实验设置

在 `02_single_tile.cu` 第 3 步注释掉这一行:

```cpp
// asm volatile("fence.proxy.async.shared::cta;");
__syncthreads();
```

保留 `__syncthreads()`,其余不变。重新编译后跑 `./judge_tile.sh 02_single_tile.cu`。

## 结果

| 版本 | judge 结果 |
|---|---|
| 带 `fence.proxy.async.shared::cta` | PASS(seed 1 / 7 / 42 / 1234 / 99999) |
| 注释掉该 fence,仅留 `__syncthreads()` | PASS(seed 1 / 7 / 42 / 1234 / 99999) |

即在本机上,漏掉 fence 仍然全部通过,没有观察到 MISMATCH。

## 分析

**为什么仍然 PASS。** `st.shared` 的写走 generic proxy,`tcgen05.mma` 读 shared
走 async proxy。`fence.proxy.async` 的作用是让前者对后者可见并定序,`__syncthreads()`
只在 generic proxy 内部对齐各线程的 shared 读写,不建立 generic→async 的跨 proxy
顺序。少了 fence,内存模型上就没有这条 happens-before 边。
本例能过是因为:tile 很小、单 block、无写竞争;而且从 `st.shared` 到单线程真正
发射 `tcgen05.mma` 之间还隔着 `__syncthreads()`、`elect.sync`、descriptor 计算等
一批指令,等 async 单元去读时写早已落到 shared / L1,于是"碰巧"读到新值。

**为什么这仍然是错的。** 这是未定义行为下的"恰好正确",不是安全代码。以下改动
都可能把这个 race 暴露成 MISMATCH:换 arch;ptxas 指令调度变化缩短写到读的间隔;
引入多 stage 流水(4.3)让写和读在时间上重叠;`tcgen05.mma` 之间的气泡被填满。
seed 只改数据值、不改时序,所以扫再多 seed 也测不出来——这也解释了为什么judge
的严格对拍在这里不足以发现问题。

**与 2.1(b).3 的关系。** 这正是 2.1(b) 第 3 条在真硬件上的验证:说法为真——
不加 `fence.proxy.async`,异步 MMA 确实"可能"读到 shared 中的旧值,只是"可能"
不等于"每次"。
